# QA / Self-Review ანგარიში — „გზა“

**სტატუსი:** წინასწარი თვითშეფასების ანგარიში. ქვემოთ მოცემულია პროექტისთვის რელევანტური პოტენციური ხარვეზები და შემოწმების სცენარები. ეს არ ნიშნავს, რომ ყველა პრობლემა რეალურ ბრაუზერში უკვე დაფიქსირდა ან გამოსწორდა; საბოლოო სტატუსი უნდა შეივსოს ხელით ტესტირების შემდეგ.

## 1. მცირე ეკრანზე მარშრუტის ტექსტის გადაფარვა

- **პოტენციური პრობლემა:** გამგზავრების ან დანიშნულების ადგილის გრძელი დასახელება, გრძელი მძღოლის სახელი ან მანქანის მოდელი 375px ეკრანზე შეიძლება შეკუმშოს მეზობელი ელემენტები.
- **როგორ მოწმდება:** Chrome DevTools → Device Toolbar → 375px; გამოიყენე დიდი სიგრძის სატესტო ქალაქებისა და მანქანის სახელები.
- **რისკი:** ღილაკის ტექსტი შეიძლება გაჭრას ან ბარათი ჰორიზონტალურად გადაცდეს viewport-ს.
- **კონტროლი/შესაძლო ფიქსი:** Grid-ის შვილებისთვის `min-width: 0`, ტექსტის მოქნილი გადატანა, ერთსვეტიანი მარშრუტების ბადე და `overflow-x`-ის შემოწმება.
- **სტატუსი:** ხელით დასადასტურებელია.

## 2. API-ის ან ინტერნეტის გათიშვა

- **პოტენციური პრობლემა:** თუ API მიუწვდომელია, მომხმარებელმა შეიძლება იფიქროს, რომ ლოკალური დემო ცვლილება სხვა მომხმარებლებსაც გაუზიარდა.
- **როგორ მოწმდება:** გააჩერე Express სერვერი, განაახლე გვერდი და სცადე მარშრუტების ძებნა, დამატება და ჯავშნის შექმნა.
- **რისკი:** ლოკალური მონაცემები მხოლოდ იმავე ბრაუზერში ინახება და სერვერს არ სინქრონდება.
- **კონტროლი/შესაძლო ფიქსი:** ყვითელი demo/cache ბანერი აცხადებს, რომ ნაჩვენებია ლოკალური დემო მონაცემები; CRUD feedback-შიც უნდა შენარჩუნდეს local-only გაფრთხილება.
- **სტატუსი:** კოდში fallback არსებობს; სერვერის გათიშვის სცენარი ხელით დასადასტურებელია.

## 3. სწრაფი ან პარალელური ჯავშნები (Overbooking)

- **პოტენციური პრობლემა:** ერთსა და იმავე ბოლო ადგილზე რამდენიმე მომხმარებელი ერთდროულად დააჭერს დაჯავშნას.
- **როგორ მოწმდება:** `npm run test:api` გაშვებულ API-ზე უნდა დაადასტუროს, რომ არასაკმარისი ადგილების მოთხოვნა იღებს HTTP 409-ს და ადგილების რაოდენობა არ იცვლება. UI-ში ასევე გამოცადე სწრაფი ორმაგი დაჭერა.
- **რისკი:** მხოლოდ ფრონტენდის `disabled` მდგომარეობა სხვადასხვა მომხმარებელს შორის საკმარისი არ არის.
- **კონტროლი/ფიქსი:** UI locking და loading მდგომარეობა; SQLite transaction და `seats_available >= requestedSeats` პირობითი განახლება სერვერზე.
- **სტატუსი:** domain validation unit ტესტები წარმატებულია; სრული API smoke test და ბრაუზერული სცენარი ჯერ გასაშვებია.

## 4. კლავიატურის/ფოკუსის ხელმისაწვდომობა

- **პოტენციური პრობლემა:** თუ მოდალის გახსნისას ფოკუსი არ გადავიდა ფორმის პირველ ველზე ან დახურვისას წინა ღილაკზე არ დაბრუნდა, კლავიატურის მომხმარებელი შეიძლება დაიკარგოს.
- **როგორ მოწმდება:** მხოლოდ Tab, Shift+Tab, Enter, Space და Escape გამოიყენე; სცადე მოდალის გახსნა/დახურვა და ვალიდაციის შეცდომები.
- **კონტროლი:** `:focus-visible`, მოდალის focus trap, Escape/overlay დახურვა და focus restoration კოდში გათვალისწინებულია.
- **სტატუსი:** ხელით დასადასტურებელია რეალურ ბრაუზერში.

## დასკვნა

პროექტში გათვალისწინებულია ძირითადი დამცავი მექანიზმები, მაგრამ თვითშეფასების ანგარიში საბოლოოდ მხოლოდ რეალური ბრაუზერული შემოწმების შემდეგ უნდა ჩაითვალოს დასრულებულად. სქრინშოტები უნდა გადაიღოს სტუდენტმა საკუთარ გარემოში; ამ დოკუმენტში გამოგონილი ტესტირების მტკიცებულებები არ არის შეტანილი.
